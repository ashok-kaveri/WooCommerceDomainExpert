# Woo Feature Prerequisites

Turns the prerequisites named on a release's cards into a checked list against
the live QA site, and says exactly what is not ready.

## Why this is not MCSL's toggle list

MCSL toggles are SaaS feature flags keyed by a merchant account UUID, applied by
the dev team as `"<accountUUID>.<flag>": true`. WooCommerce plugins are
self-hosted — there is no account UUID and no remote flag service. A prerequisite
here is one of four things:

| Kind | Where it lives | How to read it |
|---|---|---|
| **Plugin build** | the site's active plugins | `system_status` → `active_plugins` |
| **Plugin setting** | the Multi-Carrier shipping method instance | `shipping/zones/<id>/methods/<instance_id>` → `settings` |
| **WooCommerce setting** | core settings groups | `settings/<group>/<id>` |
| **Carrier registration** | the plugin's registration screen | **not readable via REST** — ask the user |

If a card genuinely describes an account-scoped flag, it is a Shopify/MCSL card
that landed on the wrong board. Say so rather than inventing a WooCommerce
equivalent.

## Inputs

- A scope: a release name/guide already generated by `woo-handoff-docs` (preferred —
  reuse its index table), or a Trello list/lane to read directly.
- Optionally a site URL. Defaults to `WOO_SITE_URL` from `.env`.

## Steps

1. **Collect the prerequisites per card.**
   - If a combined support guide exists (`data/handoff_docs/...md`), read its
     `Included Story Cards` index table.
   - Otherwise pull the lane's cards via `woo-trello-operator` and run
     `build_handoff_context` / `detect_toggles` from `pipeline/handoff_docs.py`.
   - Skip cards with nothing detected — do not invent a prerequisite.

2. **Classify each one** into the four kinds above. State the kind explicitly;
   it decides how it gets verified and who can action it.

3. **Read the live site.**

   ```python
   from pipeline.toggle_state import capture_store_and_toggle_state, compute_toggle_status

   state = capture_store_and_toggle_state()      # defaults to WOO_SITE_URL
   if state.error:
       print("partial capture:", state.error)

   print("WordPress", state.wp_version, "| WooCommerce", state.wc_version)
   for name, version in state.plugin_versions.items():
       print(f"  {name:55} {version}")

   status = compute_toggle_status(required, state.toggle_map)
   ```

   `status` splits into:
   - `enabled` — found on the site and switched on
   - `missing` — found and switched off → the actionable list
   - `unknown` — not present at all → wrong plugin version, wrong screen, or the
     card named something that is not a real setting

4. **Check the plugin build separately.** A card is untestable if the fix is not
   deployed, no matter what the settings say. Compare the active version against
   the version the card or release targets, and lead with that if it does not
   match.

5. **Report.** One block per site:

   ```
   Site      : <site url>
   WordPress : 6.x    WooCommerce : 9.x
   Plugin    : PH Multi Carrier Shipping <version>   (expected <target>)

   Ready (3)
     ✔ debug mode
     ✔ box packing
     ✔ ph_multicarrier enabled on zone "India"

   Not ready (2)
     �’ residential address detection — setting exists, currently off
     ✗ dry ice support — not found on this site (plugin version may predate it)

   Manual (1)
     ⚑ UPS carrier registration — cannot be read over REST.
       Confirm at <site>/wp-admin/admin.php?page=ph_multi_carrier_ups_registration
   ```

6. **List anything left out** with a one-line reason each — cards with no
   detected prerequisite, prerequisites you could not classify, or settings the
   REST API does not expose.

## Guardrails

- Never invent a prerequisite that is not backed by card or comment evidence.
- Never report a setting as enabled when the capture returned `unknown` — those
  are different answers and the difference matters.
- This skill is **read-only**. It changes nothing on the site. Enabling a setting
  is a `woo-store-actions` write or a human in wp-admin; say which.
- Carrier registration and licence activation cannot be verified over REST. Ask
  the user to confirm rather than guessing from indirect signals.
- `state.error` being set means the capture is *partial*. Show what you got and
  say what failed — do not present a partial capture as a complete answer.
- If the user also wants this sent to the dev team, that is a Slack send — show
  the content and target first and only send after explicit approval, unless the
  destination was named in the same request.

## Final Response

The per-site block from step 5, plus the exclusion list from step 6 if non-empty,
plus a single closing line: whether QA is unblocked, and if not, the shortest
path to unblocking.
